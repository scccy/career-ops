第二,**数仓分层**。DataWorks 上 150 个调度节点,ODS 落原始数据,DWD 做字段标准化、去重、格式清洗,DWS 按投放、用户、收入主题汇总,ADS 直接供报表。每层职责边界划清楚。

第三,**时效和权限**。XXL-Job 每渠道独立定时,渠道之间故障隔离;每天 9 点半全链路产出、ADS 10 点前;报表服务按角色和组织做数据权限。

结果是 3 个业务团队的日报、周报、收入明细全部线上化,SLA 稳定。"

### 故事 2:HikariCP 连接泄漏排查(性能排查方法论)

"我们数据同步服务在生产上出现过连接被耗尽、响应变慢的问题。我的排查分三步:

**先观测**:开 HikariCP 的 leak-detection,阈值设 120 秒,拿到连接持有超时的精确堆栈,定位到是哪段代码持有连接不放。

**再分析**:定位到是批量 upsert 的长事务,单批次太大,事务长时间占着连接。

**后根治**:定了 BATCH_SIZE=500 的分批提交规范,并且把这条规范写进了项目的工程文档里,防止复发。

这个问题给我的方法论是:**性能问题不靠猜,先观测、再定位、后规范**。这套思路放到慢 SQL 排查上一样成立:EXPLAIN 看执行计划,profile 定位到具体算子,然后优化并且沉淀成规范。"

### 故事 3:威圣统一电商数据口径(协同 + 数据治理)

"我在威圣的时候,公司是电商业务,订单数据散在淘宝、抖音、快手好几个平台,加上金蝶的财务数据、聚水潭的 ERP、还有业务部门本地的 Excel。各部门各算各的,会上数据对不上。

我做这件事的关键不是技术,是**先把人的口径对齐**:拉着运营、采购、财务逐个字段确认定义——比如【选:A. "销售额算不算退款" B. "订单口径按支付时间还是下单时间" C. "成本价取金蝶还是取聚水潭"】——确认完统一编码体系,消除歧义。

技术上用 Spring Boot + DataX 把四个数据源打通聚合,在 BI 系统统一查看,再按部门配数据权限。

最后财务的日周月报和运营报表全部统一口径产出。这件事让我坚信:**消除数据的二义性,先消除人的二义性**——这也是我理解数据治理和语义层对接的底层逻辑。"

### 故事 4:8 渠道历史补数机制(管道可靠性)

"8 个渠道靠 API 定时拉数,有两个绕不开的现实:渠道数据会延迟、会回刷修正;任务本身也可能失败。任何一天出错,下游报表就是错的。

所以我设计补数机制时先假设'它一定会失败':

- 每渠道独立 XXL-Job 定时任务,单渠道故障不扩散;
- 补数支持**指定日期范围 + 分页回放**,可以精确重拉任意历史区间;
- 写入按'渠道 + 日期'**幂等覆盖**,重跑多少次都不产生重复数据。

效果是任意日期都能回放自愈,渠道回刷、任务失败都不影响最终产出,9 点半的 SLA 就是这么保住的。

我的体会:**数据管道的可靠性 = 幂等 + 可回放**,设计时先想失败路径,再想正常路径。"

## ④ 两道决胜题完整答案

### 决胜题 1:"面向 AI Agent 的 ADS 层和传统 BI 的 ADS 有什么不同?"

"最核心的区别是**消费者变了**:传统 ADS 服务人,人看固定报表,口径藏在报表逻辑里;Agent 是机器动态生成查询,所以 ADS 必须**语义自解释**。

落到设计上是三件事:

第一,**预聚合宽表**。Agent 生成的 SQL 质量不可控,表越宽、join 越少,出错面越小。

第二,**指标元数据内嵌**。每个指标的业务定义、计算逻辑、数据来源、更新频率要结构化可查——我在奇瑞写指标开发文档就是这四要素,这正好是语义层要索引的内容。

第三,**口径唯一、命名语义化**。一张表一个业务主题,字段名一看就懂,维度枚举值字典化。

我自己在 PyPI 发过两个 MCP 协议的工具包,亲手接过 Agent 调工具的链路。我知道 Agent 消费数据最怕三件事:**口径模糊、schema 不自解释、响应慢**——这正好对应咱们 JD 里 ADS 建设、语义层对接、StarRocks 查询优化这三条职责。"

### 决胜题 2:"你用的是 ClickHouse,StarRocks/Doris 了解吗?"

"我生产上用的是 ClickHouse 和 ByteHouse,MPP 引擎的底层是通的——列式存储、向量化执行、分区裁剪这些我都实操过。

StarRocks 我系统梳理过,它相对 CK 的核心优势我理解是三个:

第一,**主键模型的 merge-on-write**,维度表频繁更新的场景比 CK 的异步 mutation 友好得多;

第二,**Colocate Join**——两张表按相同分桶键分桶,相同 hash 的 Tablet 落在同一个 BE 上,JOIN 不需要跨节点 shuffle,这对多表关联是质变;

第三,**CBO 优化器 + 物化视图自动改写**,多表预聚合可以交给引擎,CK 的 projection 只支持单表。

表模型的设计思想两边是相通的:CK 的 ReplacingMergeTree 对应 Doris 的 Unique 模型,AggregatingMergeTree 对应 Aggregate 模型。对我来说切换成本不高。"
