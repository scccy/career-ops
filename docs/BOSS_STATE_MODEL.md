# BOSS 岗位与发送状态盘点及统一规划

> 目的：统一控制台、候选检索、城市配额和批量发送对“状态”的理解，并记录状态模型与实施进度。

> 实施状态（2026-10-11）：下文“当前实现/推荐”记录的是改造前盘点。控制台与后端已按方案更新：共享预检已连接总览、岗位列表、单城发送及 CLI；人工暂缓与联系事实分开保存。未完成项见第 7 节。

## 1. 结论摘要

现在没有一个统一的“岗位状态”。至少有六种不同含义被字段、日志和页面标签分别表达：岗位是否仍有效、评分是否达标、是否联系过、近期去重/配额是否允许、人工是否复核、一次控制台命令是否完成。

当前冲突的直接来源：

- 城市卡片「池中待发」使用 `computeSendableCounts()`，会考虑评分、关闭状态、30 天岗位/公司去重、每城配额和平台配额。
- 城市链接「候选池 20」打开的却是 `greeted=0 + score≥阈值` 的数据库候选；它有意包含近期重复项，不代表可发送。
- 候选检索行标签「可发」只判断 `score≥threshold`，既没检查关闭状态，也没检查去重和配额。
- 主流程第 4 步的「查看可发队列」快捷入口也只是 `greeted=0 + minScore` 的数据库过滤，并未调用真实发送预检。
- 所以「可发」和「池中待发」目前表达不同定义。杭州原始候选 20、预检可发送 0 可以同时为真，但页面把原始候选标成“可发”，造成语义冲突。
- 总览里的全局 `pending` 查询没有排除 `status='closed'`，而城市候选计数和岗位检索会排除；因此另有一个总数口径差异。

## 2. 当前状态盘点

| 所在位置 | 当前字段/状态 | 当前含义 | 当前值/类别 | 主要问题 |
|---|---|---|---|---|
| `boss_jobs.greeted` | `0 / 1` | 是否已打招呼；发送成功后置 1 | 二值 | 批量按钮“标记已发”也直接置 1，可能只是人工排除，并非确实联系过 |
| `boss_jobs.score` | `NULL / 数值` | 是否有评分，以及评分高低 | 待评分、低于阈值、达到阈值（由阈值动态派生） | 评分资格不等于当前能发送 |
| `boss_jobs.status` | 字符串，默认空 | 目前主要记录职位关闭 | 空/其他按可用处理；`closed` 排除 | 字段名泛化，但实现只有关闭标记；未知值缺少规范 |
| `boss-sent-log.tsv` 的 `status` | 发送尝试结果 | 单次发送记录 | `sent`、`auto_sent`、`failed`、`closed` | 这是事件结果，不是岗位当前状态；多次失败/重试会有多条记录 |
| 复核文件 | `status` | 用户复核闸门 | 当前写入 `pending_user_confirmation` | 复核状态与岗位状态无关，但都叫 status |
| 控制台命令 | `job.status` | 一次扫描/发送命令的运行状态 | `running`、`done`、`failed` | 是命令状态，不是候选岗位状态 |
| 候选检索下拉 | `greeted` 参数 | 数据库筛选条件 | 全部、达标未打招呼（含近期重复）、未评分、未打招呼、已打招呼 | “未打招呼”不等于“本轮可发送” |
| 候选检索行标签 | UI 文案 | 简化显示评分/联系字段 | `可发`、`低分`、`已发` | `可发` 仅检查分数，名称过度承诺 |
| tracker | `Applied` 等 | 求职申请进度 | tracker 生命周期 | 与 BOSS 打招呼事实不同，不应反向代替 `greeted` |

### 2.1 发送日志状态的实际语义

- `sent`：自定义打招呼文案已在聊天记录中验证。
- `auto_sent`：BOSS 自动发送了默认招呼，但自定义文案未验证；已形成联系，当前被计入公司去重和每日额度，也会把岗位标记 `greeted=1`。
- `failed`：本次交互失败。通常可以以后重试；失败不应永久把岗位变成不可发送。
- `closed`：发送时确认职位已关闭；同时把数据库 `status` 标为 `closed`，后续候选查询排除。

失败记录是“尝试历史”，不能作为不可重试的终态。`closed` 才是当前明确的终止性岗位状态。

### 2.2 当前“池中待发”计算

服务端从数据库取 `greeted=0`、分数达标、非关闭的岗位，再用发送日志和配置计算预检可发送数量：

1. 30 天内同岗位/同公司去重；公司去重覆盖 `sent` 和 `auto_sent`。
2. 每家公司每轮最多选一个岗位。
3. 扣除城市每日配额；配置了平台总配额时也扣平台总配额。
4. BOSS 页面上的实时关闭/已沟通/风控状态只能在运行时确认，因此这里是本地数据预检，不是对 BOSS 实时状态的保证。

城市的 `poolPending` 是第一步之前的原始数据库候选数；`sendable` 是经过预检后的数量。它们是两种不同指标，不能共用“待发”或“可发”标签。

## 3. 推荐的统一模型：多个正交维度，不再堆一个大状态字段

岗位的“当前状态”应由几个独立维度组合而成。评分、联系事实、职位有效性和本轮资格互不覆盖。

### A. 职位有效性 `availability`

建议值：

- `unknown`：尚未核验；默认值。
- `open`：最近一次核验仍可访问/沟通。
- `closed`：明确下线，终止候选资格。

迁移上可暂时继续读取旧 `status='closed'`；空值映射为 `unknown`。将来可把字段改名/扩成受约束值，避免把任意内容当作状态。

### B. 评分资格 `qualification`（由评分数据派生，不重复存一份）

建议派生值：

- `unscored`：`score IS NULL`。
- `below_threshold`：有分数但低于当前配置阈值。
- `qualified`：达到阈值且评分结果通过硬性门槛。
- `excluded`：评分规则明确判定不进入发送池，例如可疑机会、薪资/完整 JD 等硬门槛不满足。

如果只有分数列不足以还原硬门槛，评分结果应有明确资格字段/原因码，而不能把 `score` 当作全部资格信息。

### C. 联系事实 `contact_state`

建议值：

- `never_contacted`：没有确认建立联系的记录。
- `custom_sent`：自定义文案已验证发送（旧 `sent`）。
- `auto_greeted_unverified`：平台默认招呼已发送，但自定义文案未验证（旧 `auto_sent`）。
- `manual_contact_confirmed`：仅在用户明确确认线下/手工已联系时使用。

`failed` 是尝试事件，不是联系事实；失败后仍保持原联系状态。不得用“人工排除”伪装成“已经联系”。旧 `greeted=1` 的来源需要审计：能由 `sent/auto_sent` 证明的映射为已联系，来源不明的存量不能自动猜成真实联系。

### D. 本轮发送资格 `send_eligibility`（实时派生，不持久化）

建议只由一个共享预检函数计算，供顶部指标、城市指标、检索过滤、行标签、发送队列共同调用：

- `sendable`：当前本地规则下可以进入本轮发送队列。
- `blocked_closed`：职位已关闭。
- `blocked_contacted`：已经建立联系/`greeted=1`。
- `blocked_unqualified`：未评分、低于阈值或硬门槛不通过。
- `blocked_recent_role`：30 天内同岗位已成功发送。
- `blocked_recent_company`：30 天内同公司已有成功联系。
- `blocked_city_quota`：城市额度已满。
- `blocked_platform_quota`：平台总额度已满。
- `blocked_manual`：用户明确选择暂不发送/排除。
- `city_not_configured`：岗位城市不在当前配额配置中，不进入发送队列。

如果一个岗位同时命中多条阻塞原因，列表应返回完整 `reasons[]`；计数报表可按固定优先级归入一个主原因，保证各原因数量可加总。任何时候 `sendable` 数量必须等于同一组筛选条件下的 sendable 岗位行数。

建议文案用「本轮可发送」或「预检可发送」，并保留“发送时 BOSS 实时状态仍可能变化”的说明。用户确认的业务定义是：控制台「池中待发」代表可实际进入本轮发送流程的岗位，而不是原始未打招呼数。

### E. 人工复核 `review_state`

建议值：

- `not_reviewed`
- `pending_user_confirmation`
- `approved`
- `rejected`
- `expired`（岗位/评分/发送文案变化后，先前确认失效）

复核只表示用户对“这批岗位/文案”是否授权发送，不代表该岗位当前仍符合去重和配额。发送时仍需重新预检。

### F. 发送尝试 `attempt_state`（事件日志）

将现有日志明确当作 append-only 事件，保留 `sent`、`auto_sent`、`failed`、`closed`，并可增加 `skipped`/`cancelled`（仅在确有对应事件时）。一个岗位可有多次尝试；当前联系事实从成功事件折叠得出，不能用最近一次失败覆盖之前成功联系。

## 4. 页面和接口的统一口径

建议让 UI 明确区分两个入口：

1. 城市行显示「本轮可发送 X」和「原始候选 Y」。两者可点开各自一致的列表。
2. 候选筛选里把当前“评分达标且未打招呼（含近期重复）”命名为「基础候选（未去重）」；不要称「可发队列」。
3. 新增「本轮可发送」筛选，调用共享预检结果；行标签按 `send_eligibility` 和主阻塞原因显示，例如“本轮可发”“同公司30天内已联系”“城市额度满”“职位已关闭”。
4. 当前行级“可发”不能继续仅由 `score >= threshold` 决定。若暂时不实现精确派生，应先改名为“评分达标”。
5. `send_city`、`send_city_new`、`/api/overview`、`/api/jobs`、城市跳转链接共用同一批候选判定和排序。`send_city_new` 额外套最近扫描时间范围，但仍复用基础预检。
6. 发送操作重新计算预检；执行中遇到职位关闭或平台自动招呼等实时变化时，写入相应尝试结果并更新派生状态/日志。
7. 全局 `pending` 总数也应使用同一基础候选条件，明确它是原始候选还是预检可发送，不能与城市数据混用。

## 5. 建议的实现顺序

### Phase 1：先统一术语和口径

- 明确 UI 的原始候选 vs 本轮可发送命名。
- 行状态先不再把单纯达分叫“可发”。
- 所有“可发队列”快捷入口使用真实预检结果；若还没接入共享预检，先改名为基础候选，避免假精确。

### Phase 2：共享预检服务

- 把重复规则集中成可测试的 `selectSendableJobs()`/同等纯函数，返回选中岗位和逐岗阻塞原因。
- API 的总数、城市数、候选过滤结果、城市链接与实际 CLI 队列全部使用同一实现。
- 给每次预检返回 `computedAt`、阈值/配额快照，便于解释数量；发送前重新计算。

### Phase 3：清理持久状态

- 先审计 `greeted=1` 来源和 sent-log 对照，再决定存量迁移；不能把人工屏蔽全部误迁成已联系。
- 将手工“排除/暂缓”从 `greeted` 分离为显式 `manual_exclusion`/`skip_reason`。
- 将职位有效性从宽泛 `status` 拆成受约束的 availability；保留向旧 `closed` 读取的兼容层。
- 发送日志保留为尝试事件，建立确定的折叠规则计算联系事实。

### Phase 4：迁移与验收

- 用历史日志做只读对账报告：数据库已联系、sent-log 成功、今日各城计数、原始候选、本轮可发送、各阻塞原因。
- 先 dry-run 比对“看板数量 = 发送预览数量 = 对应列表行数”，覆盖重复公司、同岗位、城市满额、平台满额、关闭、失败后重试和 auto_sent。
- 观察结果一致后再切换默认入口；保留原始候选查看功能，不把它命名为待发。

## 6. 实施前需要定下的产品规则

1. 人工点“标记已发”当前会写 `greeted=1`。它究竟表示“确实已经手工联系”，还是“以后不要再推给我”？建议拆成两个动作：「确认已联系」和「暂不发送」。
2. 同公司去重期内，一个失败岗位是否允许尝试同公司的另一个岗位？当前失败不会计入去重，成功 `sent/auto_sent` 会计入；建议维持。
3. `auto_sent` 是联系成功事实，但自定义文案未验证。建议继续占额度/公司去重，页面单独显示“平台默认招呼已发送”。
4. 已发送岗位后来变成 `closed` 时，联系历史仍应保留；可同时有 `contact_state=custom_sent` 与 `availability=closed`，不应互相覆盖。
5. 发送候选排序目前按分数优先；若同分，可否按最近扫描时间排序需明确，以保证多城市预算耗尽时各个列表可复现。

## 7. 实施结果与剩余工作

### 已实现

- `boss/boss-send-eligibility.mjs` 提供共享预检：总览计数、岗位行资格、`eligibility=sendable` 筛选、全局/单城发送队列和实际 CLI 统一调用；返回逐岗位首个阻止原因码。
- 总览顶部的“本轮可发送”按跨城市全局队列计算；城市行的“单城可发送”按该城市独立发送队列计算，故各城市数字之和不保证等于全局数字。原始候选另列为“原始候选”，两个链接各自打开对应筛选结果。原始候选数保留符合分数、未联系、未关闭的数据库候选，不扣人工暂缓；因此其数值可能大于单城可发送数。
- 岗位检索默认查看本轮可发送；可分别按联系事实、职位状态、人工暂缓和发送资格筛选。行标签显示“本轮可发送”或主要阻止原因。
- 单城发送和“发新扫”先按共享规则计算待发送队列，再显示真实确认数量；发送前仍由 Chrome 流程检查 BOSS 页面实时状态。真实发送仍保留用户确认闸门。
- 数据库新增/迁移 `contact_state`、`availability`、`manual_excluded` 和暂缓原因；旧 `greeted=1` 来源不明的记录迁为 `legacy_contact_unknown` 并阻止自动重发。
- 批量动作拆为“确认已联系”“暂不发送”“恢复暂缓”和“删除”。校招快捷动作只做暂缓，不再伪装成已联系。关闭岗位检查会跳过人工暂缓岗位。

### 尚未实现

- 预检目前对每个岗位返回一个按优先级决定的阻止原因，没有返回全部并发命中的 `reasons[]`；筛选结果和数量仍然一致。
- `availability=open` 目前表示未标记关闭，尚未区分“主动核验开放”和“未知但可尝试”；精确实时状态仍需依赖发送过程。
- 发送尝试仍以 TSV 事件日志为准，联系事实主要由成功写入的数据库状态维护；尚未提供历史日志到数据库状态的完整只读对账报告。
- 页面筛选/行状态只描述本地预检；BOSS 页面实时变化会在执行时再次判定，运行失败和真实发送均需检查命令日志。

### 后续验收建议

- 在 dry-run 下比对顶部总数、城市计数、岗位筛选行数和 CLI 队列，重点覆盖重复公司、同岗位、城市配额耗尽、平台配额耗尽、关闭、失败重试、`auto_sent`、人工确认联系和人工暂缓。
- 对旧 `greeted=1` 数据抽样核对日志；若有可证明的 sent/auto_sent 记录，可后续提供只读对账与定向修复工具，不自动猜测来源。
