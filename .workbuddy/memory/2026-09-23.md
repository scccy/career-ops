## boss-web 第三轮：一键执行引擎（用户明确要求"点一下就执行"）
- 服务端 `POST /api/run`（白名单 key → spawn 子进程）、`GET /api/run`（轮询日志/状态）、`POST /api/run/kill`（终止）。单任务串行（runningId 占用时返回 busy），20 分钟超时，输出截断保留末 120KB。
- 白名单：doctor / scan / scan_all / score / fill / review / dryrun / merge（安全档）+ send（危险档，需 confirm:true）。`send_one` / `send_one_dry` 为动态命令：逐个校验 key_hash 必须匹配 `/^[0-9a-f]{64}$/i` 后才拼进命令行。
- 命令格式（据 boss-chrome-apply.mjs:417 用法）：`npm run boss:send:one -- --key-hash h1,h2 --confirmed-review`，`--dry-run` 优先于 `--confirmed-review`；只需单个 `--` 分隔，我之前写成 `-- --confirmed-review` 是错的，已修。
- 前端：每阶段详情面板有「▶ 执行」按钮（send 为红色 danger）；检索页有「试运行 dry-run（选中）」「▶ 批量单发（选中 N）」「队列 dry-run」「▶ 群发（按队列）」；执行控制台实时 1s 轮询日志 + 状态 + 终止按钮；危险档弹确认遮罩（不可撤销提示）。
- **关键坑（必记）**：子进程必须用**登录 shell** `spawn('/bin/bash', ['-lc', cmd])`。非登录 shell 下 `node` 解析到 WorkBuddy 内置 v22.22.2，其 undici 在此环境报 `WebAssembly.instantiate(): Out of memory: Cannot allocate Wasm memory`，命令直接崩；登录 shell 走 /etc/profile.d/lan.sh → v24.21.0 正常。另把 `dirname(process.execPath)` 前置到 PATH 兜底。
- 已验证：危险档未确认返回 needConfirm 拦截、非法 hash 拒绝、非白名单拒绝、并发 busy 拦截、doctor 真跑通过（doctor 报 "Playwright chromium not installed" 是环境既有问题，非本改动引入）。
- 补充：用户反馈"主流程也要有执行按钮"——原按钮只在点节点后的详情面板里，不易发现。已把 ▶ 执行按钮直接放到流程节点卡片上（STAGE_RUNS 加 `short` 短标签，scan 两个变体并列；按钮 `e.stopPropagation()` 只执行不展开详情），详情面板保留完整命令列表。小节标题改为「主流程（卡片上 ▶ 直接执行 · 点节点看命令与入口）」。

## 第四轮：单城发送（回答"池中待发执行哪个命令"）
- 结论：「池中待发」是 MySQL 统计值（该城 `greeted=0 且 score≥阈值`），**不是命令**。`boss-chrome-apply` 没有 `--city` 参数，只按 `daily_limit_per_city` 逐城扣配额；要只投某城，必须先写只含该城岗位的临时队列（_custom.md 已写明，否则其他城市岗位会混入）。
- 新增 `send_city` / `send_city_dry`：校验城市名 → 查 `city=? AND greeted=0 AND score>=阈值 ORDER BY score DESC` → 写 `data/boss-queue-<城市>.json` → 跑 `npm run boss:chrome:apply -- --input data/boss-queue-<城市>.json --threshold <阈值> [--confirmed-review|--dry-run]`。send_city 为危险档需确认。
- 配额卡改造：「池中待发 N ↗」可点 → 跳检索页预填（该城+未发+score≥阈值）；每城加「预演」「▶ 发送此城」按钮。
- 实测：杭州生成 201 条队列，队列内城市集合仅「杭州」；dry-run exit 0 / 5.4s，逐条产出打招呼文案，**dry-run 不需要 Chrome**（真实发送才需要 CDP）。

## 第五轮：刷新时机与配额日界（关键事实）
- **配额日界不是北京时间 0 点，是每天早上 08:00**。原因：`boss-common.todayIso()` 用 `new Date().toISOString().slice(0,10)` = UTC 日期，UTC 00:00 = 北京 08:00。写入(appendSentLog)与读取(看板 / countSentCompaniesTodayByCity)都用同一函数，口径一致，配额统计准确。副作用：`appendSentLog` 的 date=UTC、time=`toTimeString()`(本地) 两列时区不一致，人工看 TSV 时凌晨记录会像"前一天"，不影响配额计算。
- 实测（北京 2026-09-24 00:21）：本地日期 09-24 但 todayIso()=2026-09-23，印证 08:00 才翻天。
- 看板刷新时机：页面加载 → 60s 自动刷新（新增，可关）→ 点「刷新数据」→ **每次任务执行结束后自动刷新**（新增，发完立刻看到配额变化）。数据实时查 MySQL + 发送日志，无缓存。已把这两条写进配额区说明。
